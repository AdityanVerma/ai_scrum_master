# Phase 1 — Persistence with Prisma/PostgreSQL

## The Main Goal

The goal of Phase 1 was:

> **Take the Sprint Proposal generated by the AI pipeline and permanently save it in a database.**

Before Phase 1, your flow was essentially:

```text
User
  ↓
AI Sprint Planner
  ↓
Sprint Proposal
  ↓
Displayed in UI
```

If you refreshed the page, the proposal was gone.

After Phase 1:

```text
User
  ↓
AI Sprint Planner
  ↓
Sprint Proposal
  ↓
Prisma
  ↓
PostgreSQL
  ↓
Persisted Sprint
```

Now the proposal can survive page refreshes and can later be retrieved, edited, assigned, executed, and used for reflection.

## 2. We Designed the Database Schema

Instead of putting the entire proposal into one JSON column, we created proper relational models.

### Sprint

Stores the overall sprint:

```text
Sprint
├── name
├── goal
├── startDate
├── endDate
└── totalEstimatedHours
```

### SprintTask

Stores individual tasks:

```text
Sprint
└── SprintTask
    ├── taskId
    ├── title
    ├── description
    ├── complexity
    └── estimatedHours
```

### TaskSkill

Stores skills associated with each task:

```text
SprintTask
└── TaskSkill
    └── skill
```

For example:

```text
TASK-001
├── Next.js
└── TypeScript
```

### TaskDependency

Stores relationships between tasks:

```text
TASK-004
   ↓ depends on
TASK-001
TASK-002
TASK-003
```

This was important because dependencies are **relationships**, not just text attached to a task.

> **Later additions:** the `Sprint` model has since gained a `status` field (Phase 3) and `functions` / `documents` relations (Phase 5). `SprintTask` gained `status` (Phase 3) and `assignedTo` (Phase 4). See the later phase docs.

## 3. We Added Relationships Between the Models


## 6. We Dealt with Prisma Postgres's Two Connection Types

This was probably the most confusing part of Phase 1.

Your Prisma development environment gave you:

```text
prisma+postgres://...
```

That works for Prisma's CLI/development tooling.

But the application runtime needed the direct PostgreSQL connection:

```text
postgres://postgres:postgres@localhost:51214/...
```

So we separated the responsibilities:

```text
Prisma CLI
   ↓
PRISMA_DATABASE_URL
   ↓
prisma+postgres://...
```

and:

```text
Next.js application
   ↓
DATABASE_URL
   ↓
postgres://...
   ↓
PrismaPg
```

That fixed the:

```text
Connection terminated unexpectedly
```

error.

## 7. We Created `saveSprintProposal()`

We created:

```text
src/lib/db/save-sprint-proposal.ts
```

This function takes your existing:

```text
SprintProposal
```

and converts it into database records.

Conceptually:

```text
SprintProposal
      ↓
saveSprintProposal()
      ↓
┌─────────────────┐
│ Sprint          │
├─────────────────┤
│ SprintTask      │
├─────────────────┤

└─────────────────┘
```

Then we added dependency persistence.

> **Later addition:** `saveSprintProposal()` now also persists the sprint's `functions` as `SprintFunction` records, so the sprint's functional scope is kept after saving.

## 8. We Handled the Task-ID Mapping

This was an important database detail.

Your AI produces:

```text
TASK-001
TASK-002
TASK-003
```

Those are **application-level task IDs**.

But PostgreSQL gives each `SprintTask` its own Prisma database ID.

So we created a mapping:

```text
TASK-001 → Prisma ID A
TASK-002 → Prisma ID B
TASK-003 → Prisma ID C
```

Then:

```text
TASK-004 depends on TASK-001
```

becomes a real database relationship:

```text
Prisma ID D
     ↓
Prisma ID A
```

That's what allows `TaskDependency` to properly reference another task.

---

## 9. We Connected Persistence to the API

Previously:

```text
POST /api/sprint-planning
       ↓
planSprint()
       ↓
return proposal
```

We changed it to:

```text
POST /api/sprint-planning
       ↓
planSprint()
       ↓
if READY
       ↓
saveSprintProposal()
       ↓
PostgreSQL
       ↓
return result
```

Importantly, if the AI returns:

```text
NEEDS_INFORMATION
```

we **don't save an incomplete sprint**.

Only:

```text
READY
```

gets persisted.

## What We Deliberately Have NOT Done Yet

* Get a specific sprint
* Edit sprint
* Delete sprint
* Assign tasks to team members
* Track task status
* Track actual hours
* Sprint execution
* Sprint completion
* Sprint reflection

Those are things we'll build on top of the persistence layer.

And that's why **Phase 2 — Sprint Retrieval** is the logical next step:

> Before we can manage saved sprints, the application needs to be able to **retrieve them from PostgreSQL**.
